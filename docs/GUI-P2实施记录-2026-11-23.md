# GUI P2 实施记录：查阅增强与重复合并（2026-11-23）

## 结论

**GUI 规划文档的 P2 三项全部落地**：重复合并向导、时间线/地点分布、照片附件管理。GUI 无头测试 **27 用例 / 312 断言全过**，全门禁通过。至此 P0/P1/P2 全部兑现。

## 一、重复合并向导（core 补算法）

- **core 新增 `service/merge_service.hpp/cpp`**：
  - `detect()`：按「姓+名」分组，出生年一致→**强烈建议**、不同→**不建议**、缺失→**可能重复**；
  - `inspect()`：字段级冲突检查（父亲/母亲/字/生年，双方均非空且不同才算冲突）；
  - `merge()`：迁移 loser 的 parent_child / union_member / event / person_name / 他人 father_id·mother_id 引用到 winner，去重后删除 loser。有冲突时**拒绝写库**并返回清单。
  - 合并前 `VACUUM INTO` 留快照（撤销依据）。
- **GUI 面板**：扫描列表（四级建议+理由）、并排对照、冲突红字高亮、快照目录、执行合并。
- 实测：同名同年 → 强烈；同年不同 → 不建议；不同父亲 → 冲突拒绝；合并后事件迁移到 winner、loser 删除、快照存在。

## 二、时间线与地点分布

- 事件按公历/农历时间升序（无日期排末尾），显示类型、主体姓名（经 PersonService 补全）、地点名（经 PlaceService 补全）、说明；类型下拉筛选。
- 地点分布按事件数排序，用 ImGui 原生 `ProgressBar` 画条形图——**零新依赖**。
- 实测两条事件按 1920/1950 升序、主体「周事件」、地点「河南」计数 2；类型筛选「迁徙」无结果。

## 三、照片附件管理（core 补基础层）

**规划原文写「走 document service」是错的**——`Document` 是谱序/凡例等篇章正文，不是照片。附件表 `attachment` 存在但此前**没有仓储与服务**，本轮补齐：

- **自实现 SHA-256**（`core/util/sha256.{hpp,cpp}`）：FIPS 180-4 算法为公有领域，零新增依赖。用途为附件去重/完整性，非安全场景。
  - 踩坑三连：① `hex()` 每字节须输出 **2** 个 hex（初版只输出1个→32字符）；② 长度字段须**大端**（初版小端）；③ `total_bits` 须用 `uint64_t`——32 位 MinGW 上 `size_t` 右移 >32 位是 UB（导致 24>>32 竟得 24）。
  - 以 NIST 标准向量校验：`sha256("abc")=ba7816bf...15ad`、`sha256("")=e3b0c442...b855` 全对。
- **core `AttachmentService`**：文件按 sha256 存到 `attachments/<sha256>`（同名即去重）、登记元数据（kind/filename/mime/size/subject/caption）、list/get/remove、内容路径查询。
- **GUI 面板**：文件导入（遗像/扫描/照片/其他）、关联人物（默认随焦点）、说明、按人物筛选、打开路径、删除。
- 实测：导入后内容文件落盘；二次导入同文件得两条元数据但共享同一 sha256；删除一条成功。

## 五、边界

- 合并的冲突检查只覆盖父亲/母亲/字/生年四个字段；其他差异（行传、谥号、配偶列表）未逐一比对。
- 合并撤销靠快照文件恢复，GUI 未做一键撤销按钮（需走备份面板的恢复流程）。
- 附件的 `mime` 固定写 `application/octet-stream`，未做扩展名→MIME 推断。
- 附件与人物只是「主体关联」；把某附件设为人物遗像（person.portrait_attachment_id）未做 GUI 入口。
- 时间线地点分布按事件计数，不是按人物出生地/迁徙路径的复杂热力。
- 本记录对应改动尚未提交。
