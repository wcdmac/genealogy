## 2. 未兑现项清点（按来源分四类）

**A. M6 验收遗留**
- 「真实家族数据试修一部谱」——至今只用合成谱（`db seed`）跑过全链路。合成谱没有同名同姓、
  侧室继配、上溯断链、缺坐标地点、农历原文混杂，**这些恰是真实修谱的日常**。

**B. 设计文档核心价值未建**
- 证据链（4.8「citation 一等公民」）：`source`/`citation`/`document` 三张表 M0 已建，域模型为零。
  连带：无证据事实清单、同事实双 citation 冲突检测（「历史数据臆补污染库」的正面回应）。
- 名号（4.7 命名体系）：`person_name` 表已建——老谱里一人多名（谱名/乳名/学名/改后名）极常见。
- `audit_log`（4.9）：表+索引已建，service 层未接线，「这条谁改的」不可回溯。

**C. spec/设计文档已承诺未实现**
- `Idempotency-Key`（spec 概览第 14 行明示；设计文档 5.2.1：24h 内重放返回首次结果）——未实现。
- 限流（设计文档 5.2.1：429 + `X-RateLimit-*`）——spec 未声明，本地模式可后置。
- 在世者脱敏（4.9/6.5）——`privacy_level` 是声明式标记，无联动逻辑。
- 写串行化队列（第 8 章风险缓解）——当前靠 SQLite WAL + busy_timeout 兜底。
- 历法下探 1583 前（第 8 章「二期补」）——明及以前精确到日不可录。
- GEDCOM 7.0（3.2 io 模块职责含 7.0）——现只支持 5.5.1。

**D. 开放问题（设计文档第 8 章，需主人决策）**
- ① 移动端：设计文档建议否（走浏览器外接）——重排采纳，M9 只做 Responsive 适配。
- ② Y-DNA/常染色体挂钩：建议二期专题，本计划不含。
- ③ 云版账号体系（自建 vs 第三方 OIDC）：影响 M8 的 ACL 设计深度，需主人定调。

## 3. 重排后的计划（M7–M9）

### M7 数据可信度（项目立户价值，最高优先）

> 设计文档 8.2：历史数据质量（攀附、臆补）污染库 → citation 一等公民 + 无证据事实清单
> + 冲突检测人工裁定。这是家谱软件区别于通用数据库的本质，排第一。

| 步骤 | 交付 | 验收门 |
|---|---|---|
| 7.1 名号 | `person_name` 域（core+spec+三端）：名号类型/起止/主名标记 | `genea person name add/list`；人物卡显示全部名号 |
| 7.2 Source/Citation | 两域全套 + 事实↔证据挂接端点（`/citations`，subject_type+subject_id+field_path） | citation 可挂到 person 的**字段级**事实；删除被引事实时 409 |
| 7.3 无证据清单 + 冲突检测 | validate 新规则：R16 无 citation 事实统计（对应旧 R15 升级）、R17 同事实两条高置信 citation 内容互斥 | `io validate` 输出「无证据事实清单」；冲突进人工裁定队列 |
| 7.4 Document | 谱序/凡例/家训/艺文/契约域（全文检索纳入 FTS） | 文档可按正文检索命中 |
| 7.5 GEDCOM SOUR 映射 | 导入器接 Source/Citation，消除当前「证据引用未建模」损失项 | 导入报告 SOUR 损失 0；往返不丢出处链 |
| **7.6 真实谱试修（入口门）** | 主人提供一部真实老谱（扫描/口述/电子谱均可），按修谱工作流全流程修 | error 清零；warning 逐条有结论；证据链覆盖关键事实 |

> 7.6 放最后但它是 M7 的真正验收：前面五步的成果要用真实数据验证——
> 合成谱验不出「族老口述与刻本矛盾」这类场景。

### M8 API 完整度与隐私

| 步骤 | 交付 | 验收门 |
|---|---|---|
| 8.1 Idempotency-Key | POST 24h 重放缓存（内存 + 库表持久化择一） | 同 key 重放返回首次结果，不重复建档 |
| 8.2 限流 | 令牌桶 + 429 + `X-RateLimit-Limit/Remaining/Reset`；spec 同步声明 | 超限返回 429 且头齐全 |
| 8.3 在世者脱敏 | `is_living + privacy_level` 联动：private 全脱敏（生卒/住址/传记）、kin 留年份；`?privacy=raw` 本地豁免（对应设计文档「GUI 显式开关」的 API 形态）；GEDCOM 导出同口径 | viewer 令牌看不到 private 在世者详情；本地 raw 可查 |
| 8.4 角色 ACL | token 的 role 从字符串变成有 ACL 的身份：viewer 禁写、editor 禁删、steward 全权 | 三角色各跑一遍越权被 403 |
| 8.5 audit_log 接线与查询 | service 写操作后写 JSON diff；`/audit?entity=` 查询端点 | 任一人物的变更史可回溯 |

> 8.3 的前置是主人对「本地豁免」形态拍板（默认 raw 免 vs 显式开）——见 D-③。
> 若主人暂不做云版，8.2/8.4 可降级为「本地单用户模式显式声明无 ACL 需求」，
> 但 spec 不得再声明未实现的行为（本次审计的教训）。

## 5. 排序逻辑（为什么这样排）

1. **M7 第一**：证据链是设计文档定义的立户价值，且 schema/规范都已备好——
   同样的工程时间，证据链对「修出一部可信的谱」的边际收益最高。
2. **真实谱试修是 M7 的门而不是独立项**：前面所有步骤的验收最终都落在
   「一部真实谱修得顺不顺」上；合成谱验不出真实的脏数据形态。
3. **M8 次之**：Idempotency-Key/脱敏/ACL 都是「spec 已承诺或安全相关」，
   属于把已声明行为做实；限流在本地模式价值有限，排在后面。
4. **M9 收尾**：规模类问题（并发/历法范围/格式版本）只在真实使用达到
   相应规模后才痛，提前做是优化不重要的变量。
