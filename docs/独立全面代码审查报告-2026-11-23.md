## 一、严重（实测可导致数据错误或崩溃）

### S1 空串可选 ID 折叠后未用于落库 → 外键失败
- **位置**：`core/src/service/person_service.cpp:19-54`（`validate_person` / `create_person` / `update_person`）
- **现象**：`validate_person` 在**局部副本** `Person p = draft` 上把空串 `father_id/mother_id/branch_id` 重置为 `nullopt`，但 `create_person` 落库用原始 `draft`、`update_person` 用原始 `p`——规范化结果被丢弃。
- **触发**：`genea person add --family-name 甲 --given-name 乙 --father ""`，或 REST/JSON 传 `father_id:""`。
- **实测**：`错误[9001]: 插入失败: FOREIGN KEY constraint failed`。
- **影响**：建档/更新直接失败（退出码非 0），GUI 表现为"保存失败"；同类缺陷在 `union_service.cpp`（place_id）、`event_service.cpp`、`branch_service.cpp`（founder/parent）同样存在。
- **建议**：校验函数改为按非 const 引用原地规范化，或让 `create/update` 使用校验后的副本落库；更稳妥是在 `person_from_json` 与 CLI 入口统一折叠空串为 `nullopt`。

### S2 负/超大世代序号导致 `vector::resize` 异常
- **位置**：`core/src/io/book_html.cpp:84-87`
- **现象**：`g = generation_of(*p)` 可能为负；`g+1` 转 `size_t` 变成巨大值，`groups.resize(g+2)` 抛异常；`g=INT_MAX` 时 `g+2` 有符号溢出（UB）。
- **触发**：库中任一人物 `generation_no = -3`（CLI `--generation -3` 可造；导入/GEDCOM/手工改库同样），随后 `io export book`。
- **实测**：`内部错误: vector too long`（导出整本失败）。
- **影响**：谱书导出 DoS；异常虽被 CLI 顶层 catch 成"内部错误"，但 GUI 排版面板无顶层异常屏障（见 M4）。
- **建议**：入口过滤 `g < 0 || g > 10000`，异常人物记入 note；`resize(static_cast<size_t>(g)+2)` 避免符号溢出。

### S3 标记文本 `indent:` 超长数字 `stoi` 抛异常
- **位置**：`core/src/io/markup.cpp:100-107`
- **现象**：`is_digits(num)` 只保证全数字，不保证在 `int` 范围；`std::stoi(num)` 无 try/catch。
- **触发**：`〔indent:999999999999999999999〕`（用户可输入的标记文本）。
- **实测**：`内部错误: stoi argument out of range`。
- **影响**：古籍版式导出失败；异常穿透 `Result` 语义。
- **建议**：手工累加并 clamp 到合理上限，或 try/catch 后写入 `out.warnings` 并当普通文本处理。

### S4 合并操作无数据库事务 → 半套合并
- **位置**：`core/src/service/merge_service.cpp:143-177`
- **现象**：只持 `write_mutex`（线程串行），但 6 条 `UPDATE` + 去重 `DELETE` + `remove(loser)` 各自 autocommit 独立提交，无 `Transaction`。
- **触发**：任一步失败——最典型是 winner 与 loser 已是同一 union 成员时 `union_member` 主键冲突；或迁移途中磁盘/约束错误。
- **影响**：关系迁了一半、loser 未删或已删但部分引用仍指向它——数据一致性破坏且无法回滚。
- **建议**：用 `Transaction tx(*db_)` 包住全部写操作（Transaction 内部已持 write_mutex），错误时析构回滚。

### S5 合并未迁移三类主体引用 → 静默孤儿
- **位置**：`core/src/service/merge_service.cpp:145-152`
- **现象**：`sqls[]` 只迁 `parent_child / union_member / event / person_name / person.father_id,mother_id`，**遗漏** `migration.subject_id`、`citation.subject_id`、`attachment.subject_id`（三表均无外键，删 loser 不报错）。
- **触发**：被合并者（loser）有迁徙记录或被 citation/附件引用。
- **影响**：证据链、迁徙史、附件归属静默失真——指向已删除人物。
- **建议**：补三条 `UPDATE ... SET subject_id=? WHERE subject_id=?`；或合并前拒绝带 citation 的 loser（参照 `PersonService::remove_person` 的 409 保护）。

## 二、高

### H1 快照预检只 prepare 不 step → 损坏快照被放行
- **位置**：`core/src/io/backup_service.cpp:66-76`（`verify_snapshot`）
- **现象**：`sqlite3_prepare_v2("SELECT count(*) FROM person")` 只解析 schema、不读表数据，随后直接 `finalize` 返回成功。
- **触发**：快照头部正常但 person 表数据页损坏。
- **影响**：`restore_database` 依据此预检放行，把坏库拷到 `target`；而旧库已被移为 `.bak-*`，故障放大。
- **建议**：至少 `sqlite3_step(stmt)` 一次并要求 `SQLITE_ROW`，检查 `finalize` 返回值；或执行 `PRAGMA quick_check`。

### H2 恢复回滚不清理残缺目标 + 残留 WAL 未处理
- **位置**：`core/src/io/backup_service.cpp:86-130`
- **现象**：① `copy_file` 中途失败会在 `target` 留下半截文件，回滚直接 `rename(moved_main, target)` 依赖标准对覆盖行为的不强保证，且逐步 `ec` 未校验；② `target` 主库不存在但残留 `target-wal/-shm` 时不清理，新库打开会回放旧 WAL。
- **触发**：磁盘满/权限错误导致拷贝中断；或上次崩溃遗留旁车文件。
- **影响**：恢复后得到被污染的库，或新旧库都打不开。
- **建议**：回滚前显式 `remove(target)` 与旁车；无论主库是否存在都先移开 `-wal/-shm`；回滚失败单独上报。

### H3 GUI 恢复路径绕过换库清理 → worker use-after-free
- **位置**：`gui/src/panels/backup_panel_state.cpp:28-40` + `backup_panel.cpp:35-41`
- **现象**：`restore_and_reopen()` 直接 `session.close()` / `open()`，**未**调用 `reset_panels_for_switch()` / `on_database_closed()`，也未停后台 worker。
- **触发**：世系树后台装载或校验后台运行时点"从快照恢复"。
- **影响**：worker lambda 持裸 `DbSession*`（`tree_panel_state.cpp:69`、`validation_panel_state.cpp:143`）访问已释放对象 → 崩溃；恢复后面板缓存与 `state_.db_path` 未刷新，显示旧库数据。
- **建议**：恢复前走与关库相同的清理入口，确保 worker join 完成；恢复后重设 `state_.db_path` 并触发重载。

### H4 `remove_person` 级联删迁徙记录绕过 citation 保护
- **位置**：`core/src/service/person_service.cpp:150-165`
- **现象**：预检只统计 person 自身及其 event 的 citation；级联删 migration 时直接 `migrations.remove(m.id)`，未做 `count_for_subject(Migration, m.id)` 检查（`migration_service.cpp:35-46` 明确有此 409 保护）。
- **触发**：某人有迁徙记录且该迁徙被 citation 引用，删除该人。
- **影响**：citation 指向不存在的 migration，证据链失真。
- **建议**：级联删除前同样检查 migration 的 citation 引用并计入 `cited`。

### H5 CLI `date convert` 中 `solar_term` 的 Result 未检查
- **位置**：`cli/src/main.cpp:738-741, 763-766, 792-793`
- **现象**：`auto st = calendar::solar_term(g.year, *term)` 后直接 `st->hour` / `st->name`，无 `if (!st)`；同文件 `cmd_date_terms:878` 对相同调用有检查。
- **触发**：节气索引对应数据缺失/年份边界使 `solar_term` 返回错误。
- **影响**：`Result::operator->` 抛 `bad_variant_access`，被顶层 catch 成"内部错误"退出码 1，掩盖真实原因。
- **建议**：三处补 `if (!st) { print_error(st.error()); return exit_code_for(st.error()); }`。

## 三、中

### M1 0007 单库迁移遗留 lineage 主体的孤儿行
- **位置**：`shared/schema/0007_single_book.sql:140`（`DROP TABLE lineage`）；对照 `0001_init.sql:127,169` 的 CHECK 允许 `subject_type='lineage'`。
- **触发**：老库升级，且库中曾有以 lineage 为主体的 event/citation（旧 REST 时代可产生）。
- **实测**：按 0001→0006 建库插入 lineage 主体的 event/citation 后执行 0007，两行仍存在而 lineage 表已删除。
- **影响**：升级后证据/事件指向不存在主体，校验与展示出现悬空引用。
- **建议**：`DROP TABLE lineage` 前把两类行 `subject_id` 重映射为 `'book'`；因 CHECK 不含 `book`，更稳妥是用 0008 重建 event/citation 并扩枚举。

### M2 CSS 字符串上下文注入
- **位置**：`core/src/io/book_html.cpp:14-27, 139`
- **现象**：`html_escape` 不转义 `'` 与 `\`，但书名被写进 CSS 单引号字符串 `@top-center{content:'<name>';}`。
- **触发**：书名 = `x';body{display:none}/*`。
- **影响**：注入任意 CSS（不能注入 script，因 `<` 已转义）；书名为用户可控数据，属存储型注入面。
- **建议**：为 CSS 字符串单独写 `css_string_escape`（转义 `\`、`'`、换行、控制字符）。

### M3 备份失败在合并路径被静默忽略
- **位置**：`core/src/service/merge_service.cpp:131-141`
- **现象**：`create_directories` 失败（`ec`）直接跳过；`snapshot_database` 失败时 `backup_path` 留空但合并继续。
- **影响**：头文件承诺"合并前自动留快照"在错误路径无声失效，合并不可逆却无回退点。
- **建议**：备份失败时中止合并或把失败写入 `MergeResult` 由调用方确认。

### M4 GUI 绘制回调无顶层异常屏障
- **位置**：`gui/src/app.cpp` 主循环 `p->draw(session_)`
- **现象**：绘制链（service 调用、`std::filesystem`、`nlohmann::json`）无 try/catch，逃逸异常穿过 `NewFrame/Render` → `std::terminate`。
- **诚实说明**：逐路径核查了高风险调用——`stoi/stoul` 均有 try/catch、排版用非抛 `json::parse` 与 `Result`，**未发现确定逃逸的具体异常路径**；此项为结构性防御缺失，非已复现缺陷。
- **建议**：`p->draw()` 外包 `try/catch(const std::exception&)`，写状态栏并跳过该面板。

### M5 派语面板"支派派语"单选状态无法保持
- **位置**：`gui/src/panels/poem_panel.cpp:17-26`
- **现象**：点"支派派语"只置**局部** `branch=true`，从未调用 `set_scope_branch(true, ...)`；下一帧 `branch = branch_scope_` 又变 false。
- **影响**：单选立即弹回"谱级派语"，支派 ID 输入框只闪一帧；`reload/set/check` 全部仍按谱级 `book` 执行——支派派语功能实际不可用。
- **建议**：切换时调用 `set_scope_branch`，直接以成员 `branch_scope_` 作为选中状态来源。

### M6 迁移校验和只存 SQL 长度，注释承诺的 SHA-256 未实现
- **位置**：`core/src/repository/database.cpp:49-50`（`checksum = std::to_string(sql.size())`，注释"M1 换 SHA-256"）
- **影响**：已应用迁移文件被修改后无法识别，"同版本不同结构"的库无法区分。
- **建议**：改存真实 SHA-256 并在 `open` 时比对。

### M7 `AttachmentService` 错误码折叠
- **位置**：`core/src/service/attachment_service.cpp:105-169`
- **现象**：`list()` 的 `while (sqlite3_step == SQLITE_ROW)` 在 BUSY/IO 错误时静默退出并返回部分结果视为成功；`get()` 把非 ROW 一律报 `NotFound`（磁盘错误也报 404）。
- **建议**：显式区分 `SQLITE_DONE` 与错误返回码。

### M8 CI vcpkg baseline 双写 + 缓存键含幽灵 glob + 无头自检退出码歧义
- **位置**：`vcpkg.json:6` vs `ci.yml:70`（baseline 双写）；`ci.yml:88` 的 `tools/vcpkg-ports/**` 已不存在；`ci.yml:182-183` 把退出码 2 一律当"无显示"，但 `main.cpp:86` 的未知参数也返回 2。
- **影响**：缓存命中可能复用不同 vcpkg 版本产物；参数拼写错误被当环境事实静默放行。
- **建议**：从 vcpkg.json 读取 baseline 注入 checkout 并纳入缓存键；参数错误改用退出码 3。

### M9 `run_all.sh` 硬编码 `.exe` 后缀
- **位置**：`tools/testdata/run_all.sh:11-12`
- **影响**：Linux/macOS 上直接失败（CI 未调用该脚本，不影响 CI）。
- **建议**：按平台拼接后缀或提供 `EXE_SUFFIX`。

## 五、确认未发现的问题类别（附证据）

1. **SQL 注入——未发现**。所有含外部输入的 SQL 均用 `?N` 占位符 + `sqlite3_bind_*`；动态拼接仅来自代码常量（`citation_repository.cpp:217` 的 switch 常量）；FTS 关键词经 `quote_fts` 转义为双引号短语，LIKE 经 `like_escape` + `ESCAPE '\'`。`backup_service::quote_sql` 正确 doubling 单引号。
2. **资源释放（stmt/句柄/内存）——未发现实质泄漏**。仓储层统一 `Stmt` RAII；手工管理 stmt 的 `attachment_service.cpp`、`merge_service.cpp`、`book_repository.cpp` 每条返回路径均 `finalize`；`sqlite3*` 两分支均 `close`；GUI 的 GLFW/ImGui 初始化与逆序 shutdown 配对；后台线程入口有 `try/catch` + join。
3. **并发——未发现明确缺陷**。`Transaction` 先锁后判 autocommit，正确处理同线程重入与跨线程排队，三条路径配对解锁；`BulkLoader` 加锁/解锁配对；`ulid` 用 `thread_local` 引擎 + `mutex` 保护单调源；数据库 FULLMUTEX + 5s busy_timeout + WAL；"预检+UPDATE"竞态由 `sqlite3_changes()==0 → Conflict` 兜住。
4. **语法错误 / 常规路径 UB——未发现**。259 个 TU 编译通过；`Result` 解引用前均有 `if (!r)` 检查（本轮新发现的两处 `solar_term` 是唯一遗漏，见 H5）。
5. **空数据库操作 / 越界索引——未发现**。15 个面板 `draw()` 首行均有 `if (!session.is_open())` 早退；`panels_[1]` 前有 `size()>1` 保护；`char[]` 全部传 `sizeof`。
6. **规则 JSON 与消费代码一致性——未发现**。`json.load` 全部通过；`rules.cpp` 读取字段与 JSON 完全对应；`validation.json` 16 条规则与 `check_table()` 注册逐一对应。
7. **许可证/依赖白名单——未发现**。实测 `license_check.py` 通过（12 项依赖，全仓无 Qt）；vcpkg 实际依赖均在 allowlist。
8. **OpenAPI 一致性——审查对象不存在**。`shared/openapi/openapi.yaml` 与 `tools/validate_openapi.py` 已在"定位收口"提交中裁撤，当前磁盘无此文件；`build/bin/openapi.yaml` 是过期构建产物（建议清理，低）。此项不构成本轮发现。
