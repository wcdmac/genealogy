## 四、关键代码审读发现

### 亮点（值得保持的工程实践）

- `auth.cpp`：验签先于 payload 解析、签名常量时间比较、默认密钥大声告警、
  `raw` 缺省保守 false——每处都有威胁模型注释；
- SQL 全参数化（core/server 抽查零拼接）；审计/幂等失败不阻断主写但 stderr
  大声报——「绝不静默」原则在位；
- 限流器：互斥完整、OPTIONS/health/openapi 豁免正确、两个实测踩坑（端口键控/
  值捕获）以注释固化；
- `sanitize_person`：历史人物不脱、kin 缩年、private 全脱，出口覆盖经 403 矩阵测试。

### 小项（无缺陷，属加固建议）

1. 限流桶表无淘汰上限——长期公网运行内存缓涨（云版 C1 前加 LRU）；
2. `audit.cpp` 重复 `#include <sqlite3.h>`（纯洁癖）；
3. postHandling 读容量在锁外（与运行时改容量的竞态仅影响响应头数字，不影响限流判定）。

### 追记：验收报告入库当晚撞出并修复的真实 flake（2026-11-18）

报告提交（0459035）的 CI run `44207302065` 在 macOS 上红——纯 markdown
提交不该挂，排查结果是一颗**真实的潜伏 flake**：audit_log 两条写入落进
同一毫秒时，ULID 随机尾随机决定排序，`/audit`「新变更在前」（id DESC）
的语义是概率性的；测试按位置断言（rows[0]=update/rows[1]=insert）偶发
翻转。此前本地连跑全绿纯属运气面，macOS runner 容量告警挤时序后暴露。

修复取引擎路线而非放宽测试：core 新增 `MonotonicUlid`（同毫秒写入时对
上一条按 Crockford 位 +1 进位，进程内严格递增），audit_write 接线——
「id 序即写入序」从此是保证而非运气（f1e3dd0，run `44209056410` 三平台
全绿，含原爆点 macOS；本地 server 测试 5 连过）。实体 id 不改用单调
生成器（会暴露写速率且引入全局锁），仓储列表的 `ORDER BY id` 仅做分页
不承诺写入序，维持原样。

### 流程发现（本次验收的实际产出）

CLI E2E 层**不在 CI 里**，是本地卡点——这正是过期期望逃过 CI 的根因。
建议 CI 增加 `run_e2e.sh` 步骤并把 `.exe` 硬编码改为按 OS 分派（与已登记的
testdata 欠账合并处理）。
