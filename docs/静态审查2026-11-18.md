## 1.3 致命（Fatal）

### F1｜`cli/src/cmd_io.cpp:808,1056-1061` · `cmd_bench`

- **问题**：`bench` 直接在全局 `--db`（默认 `genealogy.db`）上灌入基准数据，跑完无条件 `remove` 主库及 `-wal`/`-shm`。
- **可能原因**：把基准用临时库与用户业务库共用路径；`keep` 默认 false，删除前无存在性保护或确认。
- **影响范围**：任何对已有数据的库执行 `genea bench` 的场景，先污染再整库删除，数据不可恢复；默认文件名恰是常规业务库名。
- **改进方向**：强制使用系统临时目录的专属库；若坚持用 `--db`，仅在确认为本次新建且得到显式确认后删除。

### F2｜`core/src/repository/transaction.cpp:19-32,44-55` · `Transaction`

- **问题**：构造函数在 `write_mutex().lock()` **之前**用 `sqlite3_get_autocommit()==0` 判定"搭车"。
- **可能原因**：autocommit 是 sqlite3 连接的全局状态，不是线程局部状态；注释所称"跨线程会排队等锁"不成立。
- **影响范围**：server 通过 `runtime.cpp:12`、`main.cpp:146` 共享单一 `Database`。线程 B 会搭入线程 A 的事务，B 的 `commit()`（仅置 `done_`）返回成功；A 回滚则 B 的写入静默丢失。所有使用 `Transaction` 的仓储均受影响。
- **改进方向**：先取写锁再判断；或以线程局部"是否持有递归锁"判定搭车；或改为每线程独立连接。

## 1.4 高（High）

### H1｜`server/src/body_guard.cpp:73` / `server/src/routes_auth.cpp:94`

- **问题**：UTF-8 守卫仅对 `Content-Type: application/json` 生效，所有 JSON handler 却无条件 `json::parse(req->body())`。
- **可能原因**：守卫与解析的触发条件不一致，改请求头即可绕过。
- **影响范围**：非法字节可进入解析器；守卫头文件记录了 GBK body 导致进程级终止的实测事故，匿名 `/auth/token` 亦可达。若第三方新版仅抛异常则降级为输入校验缺陷。
- **改进方向**：对所有请求体做 UTF-8 校验，或 handler 强制校验 Content-Type。

### H2｜`cli/src/cmd_backup.cpp:189-203` · `cmd_db_restore`

- **问题**：`--force` 先将活库 `rename` 为 `.bak-*` 并打印成功，随后才校验 `--from` 目录。
- **可能原因**：破坏性操作置于前置校验之前，缺少补偿事务。
- **影响范围**：路径写错或备份损坏时旧库已被移走、新库未落地，业务中断。
- **改进方向**：先验证备份目录、快照文件与可读性再移库；拷贝失败时将 `.bak` 改回原名。

### H3｜`cli/src/cmd_backup.cpp:189-191,233` · `cmd_db_restore`

- **问题**：`--force` 只搬主库，残留 `-wal`/`-shm`。
- **可能原因**：按单文件模型处理 SQLite。
- **影响范围**：WAL 帧被重放到新库，恢复数据被旧事务污染。
- **改进方向**：同步搬走旁车文件，或恢复前以正式连接完成 checkpoint。

### H4｜`server/src/main.cpp:48-50,68-70` · `parse_args`

- **问题**：`require_auth` 默认 false 且 `--host` 可独立设为 `0.0.0.0`，两者无联动校验。
- **可能原因**：绑定地址与鉴权开关缺 fail-fast（口令/JWT 密钥有，唯独此组合没有）。
- **影响范围**：误配对外部署时全库匿名读写，`local_identity()` 给予全权 steward 与 `raw_privacy=true`。
- **改进方向**：非回环地址强制要求 `--require-auth`，否则拒绝启动。

### H5｜`server/src/idempotency.cpp:40-46,75-83`

- **问题**：幂等键直接取客户端 `Idempotency-Key`，不含用户名与端点维度。
- **可能原因**：缓存表键设计为全局单列。
- **影响范围**：启用鉴权后不同用户可命中对方缓存响应（信息泄露），同一 key 跨端点错误复用。
- **改进方向**：使用复合键 `(username, endpoint, key)` 或按用户哈希隔离。

### H6｜`core/src/io/gedcom.cpp:228-242,246-263`

- **问题**：`build_subtree` 与 `merge_continuations` 均为无深度上限的递归。
- **可能原因**：解析前未约束 level 跨度。
- **影响范围**：外部上传的畸形 GEDCOM 可致栈溢出，导入进程/服务崩溃。
- **改进方向**：改显式栈迭代，或超限返回 `IoError`。

### H7｜`core/src/lineage/tree.cpp:9-54`

- **问题**：`expand` 无 visited 集合，`descendants_list` 的 BFS 也无 visited。
- **可能原因**：`tree.hpp:28` 明示 `max_depth<=0` 不限制且"可能有环"，却未做防护。
- **影响范围**：环数据下递归栈溢出或队列无限增长；CLI、REST、GUI 的树查询均可触发。
- **改进方向**：按当前路径维护 visited，并在上层约束 `max_depth>0`。

### H8｜`core/src/repository/citation_repository.cpp:174-198`

- **问题**：`count_for_subject/count_for_source` 在 prepare/step 失败时返回 `0`。
- **可能原因**：数据库错误被折叠成"无引用"。
- **影响范围**：`person_service.cpp`、`source_service.cpp` 等的删除保护失效，被引用记录可被删除并留下孤儿 citation，客户端收到 200。
- **改进方向**：返回 `Result<int>`，查询失败时中断删除。

### H9｜`clients/web/src/views/TranscribeView.tsx:352,390,415-423,854`

- **问题**：主暂存路径 `fatherKey` 恒为 null（父名只写入展示字段），"生子"按钮传伪 key `"local"`。
- **可能原因**：真实父条目 key 未传导；`commitAll` 遇到未解析的 fatherKey 直接 `break`。
- **影响范围**：欧式连书的父子关系建不上，且单条即可中断整批入库。
- **改进方向**：写入真实父 key；单条失败改为跳过而非终止全批。

### H10｜`clients/web/src/context.tsx:45-49`

- **问题**：登录凭据硬编码 `("web","web")`，UI 无输入。
- **可能原因**：仅按本地免鉴权模式设计。
- **影响范围**：服务端启用 `--require-auth` 后 Web 端完全不可用，凭据无法轮换。
- **改进方向**：提供凭据输入/配置注入，并检测服务端鉴权模式。

### H11｜`gui/src/panels/person_card.cpp:152-157,205-207`

- **问题**：`loaded_rev_` 从未用于更新，保存时取当前库最新 `rev` 写回。
- **可能原因**：把"最新值"当作写回底稿；注释声称的 409 并发保护未实现。
- **影响范围**：多端并发编辑静默覆盖他人修改。
- **改进方向**：写回前设 `p.rev = loaded_rev_`，冲突时提示重载。

### H12｜`core/src/service/person_service.cpp:105-145` / `person_repository.cpp:287-295`

- **问题**：删除人物只清事件与迁徙，不清 `parent_child`、`union_member`、`person_name`、`branch.founder_person_id` 等引用；schema 外键无 `ON DELETE CASCADE`。
- **可能原因**：缺少显式级联清理；FK 错误统一映射 Internal。
- **影响范围**：有亲属/婚姻关系的真实人物删除必然 FK 失败，返回 500 而非 409。
- **改进方向**：显式定义级联或事务内清理依赖表，并归一化 FK 错误码。

### H13｜`server/src/main.cpp:315` / `server/src/routes_misc.cpp:348-350`

- **问题**：请求体上限 512 MB，multipart 全内存持有后再 `content.assign()` 复制一份。
- **可能原因**：为兼容大导入放宽上限却无流式处理。
- **影响范围**：单请求可占 GB 级内存，配合匿名写端点形成 DoS。
- **改进方向**：显著降低上限，大导入走 CLI/流式落盘。

### H14｜`core/src/lineage/rules.cpp:66-101,123-142` / `mourning.cpp:92-97`

- **问题**：规则 JSON 解析失败静默返回空表；`mourning_grades().at(rule->grade)` 与硬编码枚举表双源校验，JSON 缺项时抛未捕获 `out_of_range`。
- **可能原因**：解析失败被当作合法空状态；校验源与取值源不一致。
- **影响范围**：称谓/五服全量降级为兜底，特定数据漂移下请求线程异常终止。
- **改进方向**：解析失败显式报错，用 `find()` 替代 `.at()`，统一元数据源。

## 1.5 中（Medium）

### M1｜`core/src/model/genealogy_date.cpp:208-222`

`from_json` 直接 `get<std::string>()` 接收 gregorian/era.year，绕过 `from_iso` 校验；DTO 反序列化走独立路径。影响：`9999-99-99`、越界年号可落库，破坏排序键与干支推算。改进：复用 `from_iso` 与年号范围校验。

`chinese_number(100)` 起 `kDigits[tens]` 越界读；1..99 的契约只写在注释里。影响：公开 API 误用或未校验的大年号导致 UB。改进：`n>99` 返回空或扩展百位处理，`era_display` 同步校验。

### M5｜`core/src/service/person_name_service.cpp:24-32`

`clear_primary` 与 `insert` 不在同一事务（头文件已含 `transaction.hpp` 却未用）。影响：两步之间失败留下"主名被清、新名未插"的半更新。改进：事务内完成两步后提交。

### M7｜`core/src/io/tree_render.cpp:15-39`

DOT/Mermaid 节点标签直接拼接姓名，未转义 `"`、`\` 与换行；只防了键注入未防值注入。影响：导入的异常姓名可破坏图语法或注入额外语句。改进：输出前做标签转义。

### M8｜`shared/openapi/openapi.yaml:429-434,874-876,1568`

### M9｜`core/src/repository/migration_repository.cpp:62-74`

`subject_id` 与 `branch_id` 条件用 `AND`，与紧邻注释"或的关系"相反。影响：组合过滤结果为空，当前仅靠 REST 层 if/else 规避。改进：改为并集语义或接口层强制互斥。

### M10｜`core/src/repository/person_repository.cpp:202-205` / `server/src/problem.cpp:82`

所有 SQLite 约束/锁错误统一映射为 500，`sqlite3_errmsg()` 原文回显 `detail`。影响：客户端无法区分可重试错误，且可探测表/列/约束名。改进：集中映射 errcode→ErrorCode，Internal 错误统一替换 detail。

### M11｜`server/src/auth.cpp:350-433` / `routes_auth.cpp:122-127` / `audit.cpp:69-71`

### 2.1a 二轮裁定（2026-11-21，同日）：两项登记判断的纠正与补全

首轮登记的 5 项中，有两项经裁定不成立或应修，当日处置；三项维持登记：

- **L6 actions SHA——误判纠正，立即修**：「GitHub 匿名 API 限额拿不到
  SHA」是错误前提——限额只覆盖 REST API，git 协议不受限。实测匿名
  `git ls-remote` 直接取得全部 4 个 action 的 commit SHA（均为
  lightweight tag，返回 hash 即 commit SHA）：checkout
  `11d5960a…`、msvc-dev-cmd `0b201ec7…`、cache `0057852b…`、
  upload-artifact `ea165f8d…`。ci.yml 5 处 `uses` 已改为 SHA 固定，
  行尾注释保留标签名便于识别——与 vcpkg baseline、pip 版本固定同一
  纪律（可变标签 = 上游移 tag 即改 CI 输入）。结论翻转条件：若不接受
  手动维护 SHA 升级（每次升级改 5 处），可退回标签——那是明确取舍，
  不是「做不到」。
- **M13 AbortSignal/stale-guard——纯遗漏，当轮补全**：`RequestOptions`
  早有 `signal?: AbortSignal` 类型定义，但 PersonsView/TranscribeView
  的实际列表请求均未传 signal、无过期响应守卫——快速切换筛选时旧
  响应覆盖新结果是真实竞态。已修：listLineages/listBranches/
  listPersons/search 暴露 `options.signal`；四个加载 effect cleanup
  中 abort + `aborted` 守卫（AbortError 不进错误条）。
- **M13 origin 边界——轻量版而非硬白名单**：硬白名单与 README 明确
  支持的「同机跨端口填 http://127.0.0.1:8080/api/v1」冲突。落地为三
  件事：scheme 校验（http/https 或同源相对路径，无 scheme 的
  `localhost:8080` 此前会静默产出坏 URL，一并堵掉）；外域（hostname
  不同）连接前 `confirm` 显式确认去向；换址/断开前显式清旧令牌
  （`clearToken()`，不依赖实例替换的 GC 时序）。同主机跨端口与同址
  重连不打扰。
- **M11 jti/撤销表——维持登记，前置依赖未具备**：撤销表以用户身份为
  键，账号体系（自建 vs OIDC）是 ROADMAP 开放问题③，提前做等于给
  不存在的用户建表；审计 actor 自填同源。上云时随账号体系一并实施。
